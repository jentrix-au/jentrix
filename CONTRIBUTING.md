# Contributing to the Jentrix open client

This repository holds the three client packages of Jentrix — `@jentrix/cli`
and the official Claude Code and Codex plugins. The hosted service and its
contract are Jentrix's; the client is open so you can inspect it, verify what
runs on your machine, fix what is broken, and build your own plugins beside
it. Contributions are welcome within that scope, and Jentrix keeps merge and
publish authority.

## Before you start

- **Bugs** — open an issue with the bug template. Say which layer you think
  is at fault (service, CLI, official plugin, custom plugin); `jentrix session
  doctor` reports versions, install source, marketplace ownership, hook
  pinning and contract state, and `jentrix session doctor --bundle` writes a
  redacted file you can attach.
- **Security** — never in a public issue. See [SECURITY.md](./SECURITY.md).
- **Features** — open an issue first. The scope here is narrow on purpose:
  the CLI is a thin client over the documented MCP contract, and the official
  plugins carry provider-facing content only. A workflow that is specific to
  your organisation belongs in your own plugin ([docs/forks.md](./docs/forks.md),
  [docs/authoring-claude.md](./docs/authoring-claude.md),
  [docs/authoring-codex.md](./docs/authoring-codex.md)), not in the official
  one.
- **Provider parity is defined by intent.** A named workflow exists on both
  providers where each supports it; the file formats are not forced to match.

## Build and test

Node ≥ 20 and pnpm 11. The repository is one pnpm workspace with three
packages: the CLI at the root, `plugins/claude`, `plugins/codex`.

```bash
pnpm install
pnpm typecheck
pnpm test                      # unit tests (node:test)
CLI_PACK_SMOKE=1 pnpm test     # plus the cold install of the packed tarballs
pnpm validate:examples         # the reference extensions under examples/
pnpm gen:workflows             # after editing shared workflow sources
pnpm build                     # dist/ — the bins and the @jentrix/cli/core entry
```

`CLI_PACK_SMOKE=1 pnpm test` is what CI runs: it packs all three packages,
installs the exact tarballs together into an empty project and runs the
installed `jentrix`. Run it before opening a pull request that touches
packaging, `scripts/`, or anything under `plugins/`.

The seven official workflows have one provider-neutral source under
`plugins/workflows/`, plus short Claude/Codex entries and frontmatter. Generate
with `pnpm gen:workflows`; include both sources and generated files in the
review. Build/prepack reject stale files, and tests prove deterministic
regeneration and complete workflow availability in each packed plugin.

Session command registration lives in `src/commands/session.ts`; state,
provider context, host control, connect, alignment, status, close, and doctor
logic live under `src/session/`. Shared MCP parsing/task lookup are in
`src/tool-client.ts` and `src/task-resolution.ts`. OAuth rotation is maintained
in `src/oauth-session.ts` over `src/config.ts` and `src/oauth.ts`; the host
keeps only its long-lived coordination policy. Core's dependency firewall
remains separate.

To try a change to a plugin in your own Claude Code or Codex: register the
checkout's plugin directory as a SECOND marketplace under a name of your own
(never `jentrix`), install from it, and remove it afterwards — the official
installer refuses to repoint the `jentrix` marketplace at a checkout, on
purpose. [docs/hooks-security.md](./docs/hooks-security.md) explains what the
provider's trust prompt is protecting when you do that.

## The contract this CLI is built from

`surface.json`, `contract-vectors.json` and `contract.json` are generated by
`scripts/adopt-contract.mjs` from the contract bundle the production
deployment serves (`https://tm.jentrix.ai/api/mcp/contract`) and are never
edited by hand; the help goldens under `test/golden/` derive from them.
[docs/compatibility.md](./docs/compatibility.md) explains the surface, the
API release and the digest. A pull request that changes these files is a
contract adoption, and its description says which digest it adopts.

## Pull requests

- One change per pull request, with a test where the change is testable.
- Keep the dependency firewall: the core modules (`test/firewall.test.ts`)
  import only `@modelcontextprotocol/sdk`, `node:` builtins and each other.
- Update the doc that owns the behaviour you changed, in the same pull request.
- Do not bump versions or touch `.github/workflows/release.yml`,
  `.github/scripts/`, `plugins/*/package.json` or the provider manifests
  unless the change is about them; releases are cut by the maintainers
  ([docs/releasing.md](./docs/releasing.md)).
- Reserved names stay reserved: `@jentrix/cli`, `@jentrix/plugin-claude`,
  `@jentrix/plugin-codex` and the marketplace/plugin name `jentrix`
  ([TRADEMARKS.md](./TRADEMARKS.md)).
- Nothing that carries a credential, a transcript, or a real account or path
  lands in a fixture. Test values are synthetic and obviously so
  (`tm_0123456789abcdefTOKEN`).

Every pull request runs the `ci` workflow (typecheck, version guard, unit
tests, the cold-install smoke, example validation) and needs one approving
review from a code owner ([.github/CODEOWNERS](./.github/CODEOWNERS)).
Changes to hooks, installers, manifests or workflows get a security-minded
review on top of the ordinary one.

## Developer Certificate of Origin — sign your commits

There is no contributor licence agreement. Instead every commit carries a
[Developer Certificate of Origin](https://developercertificate.org/) sign-off,
which states that you wrote the change or have the right to submit it under
this repository's MIT licence:

```bash
git commit -s -m "fix(plugin): …"
```

`-s` appends `Signed-off-by: Your Name <you@example.com>` using your git
identity; the name and address must be real enough to reach you. A pull
request whose commits lack the line is not merged until they are amended
(`git commit --amend -s`, or `git rebase --signoff` for several).
